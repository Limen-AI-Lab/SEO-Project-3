好，按**设备策略=2**来定稿：

- **全站不限制“一个设备只能注册一次”**
- 只做你要的：**同一码最多 10 台设备完成注册**（device 去重计数），外加 `new_user_only` 仅用 **email 唯一** 来判定。

下面是“最终可交付给工程”的定稿规格（无代码）。

------

## 1) 最终验收口径（强约束清单）

### 1.1 注册门禁（必须）

用户注册前必须输入邀请码，且满足：

1. **邀请码有效**
   - `status=active`
   - `valid_from <= now <= valid_to`
2. **次数未用完**
   - `used_count < max_uses`
3. **邮箱域名允许（A）**
   - `email_domain ∈ allowed_email_domains`
4. **新用户（new_user_only）**
   - `users.email` 不存在（email 唯一）
5. **邮箱验证必需**
   - 只有当邮箱验证通过后，才能完成注册并消耗次数
6. **设备上限（B，N=10）**
   - 对同一个 `invite_code_id`，已完成注册的去重 `device_id_hash` 数量 < 10
   - 如果当前设备是“新设备”（该 code 下没出现过），加入后不能超过 10

### 1.2 邀请者奖励（即时）

- 触发：兑换 `completed` 成功后立刻发放
- 金额：`credits=10`
- 过期：`expires_at = granted_at + 30 days`
- 可撤销：后台可以将该笔奖励标记 `reversed`

> 如果某些门禁码没有码主（owner_user_id 为空），则不发奖励。

------

## 2) 数据模型定稿

### 2.1 `invite_code`

必需字段：

- `id`
- `code_hash`（唯一，建议只存 hash）
- `code_prefix`（便于后台搜索）
- `status`：active/paused/revoked
- `max_uses`, `used_count`
- `valid_from`, `valid_to`
- `new_user_only`（true）
- `require_email_verified`（true）
- `allowed_email_domains`（数组）
- `device_limit_per_code`（固定 10，但仍建议字段化）
- `owner_user_id`（可空）
- `credits_amount`（10）+ `credit_ttl_days`（30）（可放到 plan，也可直接放 code/batch 配置）
- `batch_id`
- `reserved_count`（推荐，用于预占用）

索引/约束建议：

- `unique(code_hash)`
- `index(batch_id)`
- `index(status, valid_to)`
- `index(code_prefix)`

### 2.2 `invite_redemption`

字段：

- `id`
- `invite_code_id`
- `redeemer_user_id`（complete 后写）
- `redeemed_email`（快照）
- `device_id_hash`（快照）
- `state`：reserved/completed/failed/reversed
- `fail_reason`
- `reservation_expires_at`
- `created_at`, `completed_at`

索引/约束建议：

- `unique(invite_code_id, redeemed_email)`（同一码同邮箱不重复占用/重复完成，防并发与重试）
- `index(invite_code_id, state)`
- `index(device_id_hash)`

### 2.3 `benefit_ledger`

字段：

- `id`
- `user_id`（邀请者）
- `benefit_type=credits`
- `amount=10`
- `source_type=invite`
- `source_id=invite_redemption_id`
- `status=active/reversed`
- `granted_at`, `expires_at`, `reversed_at`

约束建议：

- `unique(source_type, source_id, user_id)`（防重复发放）

------

## 3) 核心流程（两阶段，解决并发/中断/重试）

### 3.1 Reserve（预占用，不消耗 used_count）

输入：`email + code + device_id`

校验：

- code 有效、未过期、未停用
- 域名允许
- `users.email` 不存在（new_user_only）
- 设备上限校验（建议 reserve 阶段就校验，减少走完验证才失败）
- 次数校验：要用 **(used_count + reserved_count) < max_uses** 来挡并发抢码

动作：

- 写 `invite_redemption(state=reserved, reservation_expires_at=now+15m)`
- `reserved_count += 1`

返回：`reservation_id`

### 3.2 Email Verify（邮箱验证）

用户完成邮箱验证码验证。

### 3.3 Complete（完成兑换 + 创建用户 + 消耗次数 + 发奖）

输入：`reservation_id`

事务内：

1. reservation 未过期且 `state=reserved`
2. 再次校验：code 仍 active、域名仍允许、email 仍未被注册、设备上限仍满足、名额仍满足
3. 创建用户（email 唯一约束兜底）
4. `invite_redemption -> completed`（写入 `redeemer_user_id`）
5. `reserved_count -= 1` 且 `used_count += 1`
6. 若 `owner_user_id` 存在且不等于 redeemer：写一笔 `benefit_ledger(active, amount=10, expires_at=now+30d)`

### 3.4 过期清理（防占坑）

定时任务扫描 `state=reserved && reservation_expires_at < now`：

- 标记 failed
- `reserved_count -= 1`

------

## 4) 设备上限（N=10）的计算口径（明确到可实现）

对某个 `invite_code_id`：

- `completed_device_count = count(distinct device_id_hash) where state=completed`
- 若当前设备已在 completed 里出现：允许（不增加计数）
- 若当前设备未出现：要求 `completed_device_count < 10`（reserve/complete 均检查）

> 你选的策略 2 不限制“设备全站唯一”，所以这里只做“同一码下去重设备数”限制。

------

## 5) 后台功能验收点（你说需要的 5.3）

### 邀请码批次生成

- 批次配置：有效期、max_uses、allowed_email_domains、device_limit_per_code=10、是否带码主/奖励
- 生成 N 个码：导出明文 CSV（只在生成时可见明文，系统只存 hash）

### 管理操作

- pause/resume/revoke
- 查看兑换记录（按码、按批次）
- 查看某码的：used_count / reserved_count / completed_device_count

### 回滚能力（你明确要）

- 撤销某条兑换对应的奖励：把对应 `benefit_ledger` 标记 `reversed`
- （可选）将兑换标记 `reversed`（用于审计；一般不建议把 used_count 直接减回去，除非你有明确“退回名额”的业务需求）
